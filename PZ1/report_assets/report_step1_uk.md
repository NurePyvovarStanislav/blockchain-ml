## 2.1. Реалізація гаманця та цифрового підпису транзакцій

На першому етапі практичної роботи реалізовано програмні компоненти гаманця та підписаної транзакції. Для генерування ключів і створення цифрових підписів використано алгоритм Ed25519 та бібліотеку `cryptography`. Логіку формування транзакцій, обчислення адрес та підготовки даних до підписування реалізовано в межах навчального проєкту.

Гаманець створює пару криптографічно пов'язаних ключів. Приватний ключ використовується для підписування транзакцій і не передається іншим вузлам. Публічний ключ застосовується для перевірки підпису. Адресу користувача визначено як SHA-256 від 32-байтового публічного ключа у форматі Raw:

**Address = SHA256(PublicKeyBytes).**

У структурі транзакції передбачено адресу відправника, адресу отримувача, суму, комісію, порядковий номер операції (nonce), ідентифікатор мережі, версію протоколу, публічний ключ відправника та цифровий підпис.

**Таблиця 2.1 — Поля підписаної транзакції**

| Поле | Тип у Python | Призначення |
|---|---|---|
| version | int | Версія формату транзакції |
| network | str | Ідентифікатор навчальної мережі |
| sender | str | Адреса відправника, SHA-256 публічного ключа |
| recipient | str | Адреса отримувача |
| amount | int | Сума переказу в мінімальних одиницях |
| fee | int | Комісія за транзакцію в мінімальних одиницях |
| nonce | int | Порядковий номер транзакції відправника |
| public_key | str | Публічний ключ Ed25519 у HEX-форматі |
| signature | str | Цифровий підпис Ed25519 у HEX-форматі |

Для забезпечення детермінованого байтового представлення підписуваних даних застосовано серіалізацію JSON із сортуванням ключів, без необов'язкових пробілів та з кодуванням UTF-8. Поле `signature` не включається до повідомлення, яке підписується. Підпис обчислюється над визначеним набором полів транзакції.

Під час перевірки вузол спочатку визначає адресу з наданого публічного ключа й порівнює її з полем `sender`, після чого перевіряє цифровий підпис над серіалізованим повідомленням. Така перевірка встановлює відповідність підпису ключу та цілісність підписаних даних, але не перевіряє наявність коштів на балансі. Перевірка балансу, черговості nonce та дублікатів передбачена наступним етапом реалізації мемпулу.

У проєкті також передбачено збереження приватного ключа у зашифрованому файлі PEM у форматі PKCS#8, захищеному паролем. Приватні ключі не розміщуються у репозиторії.
